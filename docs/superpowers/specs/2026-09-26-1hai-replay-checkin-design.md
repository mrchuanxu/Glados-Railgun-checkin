# 一嗨静态重放自动签到设计

## 背景与验证结论

一嗨 iOS 客户端通过 `POST https://app.1hai.cn/SignCenter/UserAssets/SignIn` 完成签到。请求体、`AppIdentity`、`noncestr`、`Authorization` 和 `ehiContent-MD5` 由客户端协议生成，响应业务内容封装在加密的 `Result` 字段中。在只有 HTTPS 抓包、没有可调试 App 或解密 IPA 的条件下，不尝试推导其加密与签名算法。

2026-09-26 已使用 2026-09-19 捕获的同一组请求数据进行跨日重放。服务端返回 HTTP 200 和非空 `Result`，随后在一嗨 App 中确认当天已签到且积分增加。因此当前服务端接受完整历史请求，自动签到可先采用静态重放，而无需生成新的协议字段。

此结论只表示当前登录态和服务端规则下重放有效，不保证长期兼容。Token 失效、服务端增加防重放校验、接口协议变化或 App 升级都可能使方案失效。

## 架构

一嗨签到与现有 GLaDOS/Railgun 逻辑保持隔离：

- 新增独立 Python 脚本 `ehigh_checkin.py`，只负责配置读取、请求重放、响应结构校验和安全日志。
- 新增独立 GitHub Actions 工作流，不复用 GLaDOS 的 Cookie、兑换状态、每日完成门控或通知流程。
- 不修改 `checkin.py` 的现有职责，任一平台失败不影响另一平台运行。
- 所有捕获的认证及协议字段均由 GitHub Actions Secrets 注入，不写入仓库、测试数据、状态文件或日志。

首版只支持一个一嗨账号。多账号会扩大 Secret 配置和失败隔离范围，在出现实际需求后另行设计。

## 配置与秘密管理

脚本从以下环境变量读取请求数据：

| 环境变量 | 内容 | 必需 |
|---|---|---|
| `EHI_TOKEN` | 请求头 `Token` | 是 |
| `EHI_APP_IDENTITY` | 请求头 `AppIdentity` | 是 |
| `EHI_AUTHORIZATION` | 请求头 `Authorization` | 是 |
| `EHI_CONTENT_MD5` | 请求头 `ehiContent-MD5` | 是 |
| `EHI_NONCESTR` | 请求头 `noncestr` | 是 |
| `EHI_REQUEST_ROOT_ID` | 请求头 `x-ms-request-root-id` | 是 |
| `EHI_REQUEST_BODY` | 原始 64 字符加密请求体 | 是 |
| `EHI_COOKIE` | 原始 Cookie | 否 |

虽然 `x-ms-request-root-id` 看起来是追踪标识，但当前实验没有单独验证它能否安全替换。为严格复现已验证请求，脚本从环境变量读取并原样发送。它不属于账号密钥，但统一通过 Secret 配置可以避免将捕获数据提交到仓库。

Cookie 在现有重放实验中随请求发送，但尚未证明是认证所必需。实现允许配置 Cookie，以忠实复现已验证请求；未配置时不发送该请求头。正式部署前先用新凭据进行一次无 Cookie 手动验证。如果签到仍成功，则生产配置不保存 Cookie；否则将其作为 Secret 注入。

当前会话中公开过的 Token、Cookie、请求体及签名字段视为已泄露。部署前必须重新登录并捕获一组新的签到请求，将新值直接配置到 GitHub Secrets，不得提交到 Git 历史。

## 请求行为

脚本向固定 URL `https://app.1hai.cn/SignCenter/UserAssets/SignIn` 发送 POST 请求，并设置固定的客户端元数据：

- `Accept: */*`
- `Content-Type: application/json`
- `Accept-Language: zh-CN,zh-Hans;q=0.9`
- `AppVersion: 7431`
- `AppPlatform: iPhone`
- 抓包中已验证的 iOS User-Agent

认证和协议字段直接使用环境变量值。请求体按原始字符串发送，不进行 JSON 编码、换行、字符替换或签名重算。HTTP 客户端自行计算 `Content-Length`，避免配置值与实际字节数不一致。

请求使用 10 秒连接超时和 30 秒读取超时。网络异常、超时和非 2xx 状态都作为失败处理，不自动重试。首版工作流每日仅运行一次；不透明接口上的自动重试可能造成无法观测的重复业务操作，不在当前范围内。

## 响应与结果判定

响应按以下层级检查：

1. HTTP 状态必须是 2xx。
2. 响应体必须能解析为 JSON 对象。
3. JSON 必须包含非空字符串 `Result`。

全部满足时，脚本记录“请求已被服务端接受”并以退出码 0 结束。由于无法解密 `Result`，程序不能区分首次签到成功、今日已签到或被加密封装的业务错误，也不会在日志中声称积分必然增加。

HTTP 非 2xx、JSON 无法解析、`Result` 缺失或为空时，脚本记录安全错误并以非零退出码结束，使 Actions 运行标红。完整响应密文不写入日志；可记录响应长度和 SHA-256 摘要用于比较与排障。

## 调度与运行

新增的一嗨工作流支持 `workflow_dispatch` 和每天一次的 `schedule`。定时表达式为 `17 1 * * *`，即计划在北京时间 09:17 执行，避开 UTC 整点及现有 GLaDOS 高频窗口。文档同时标明 GitHub Actions 的定时任务可能延迟或丢失。

一嗨接口本身已表现出重复调用能力，首版不增加跨运行状态 Cache。这样避免为单次请求引入额外状态复杂度。手动执行与定时执行采用相同行为，用户应知晓同一天手动运行可能形成重复签到请求。

工作流使用当前仓库一致的 Python 版本，安装 `requests` 后运行独立脚本。只向该步骤注入一嗨 Secrets，其他诊断和第三方 Action 不接触凭据。

## 日志与安全

允许输出：

- 执行时间和目标接口路径。
- HTTP 状态码。
- `Result` 是否存在、密文长度及 SHA-256 摘要。
- 配置缺失的环境变量名称。
- 不包含请求数据的网络错误类型。

禁止输出：

- 任一 Secret 的值或局部值。
- 完整请求头、请求体、Cookie 或响应 `Result`。
- 可能把请求对象和环境变量展开的调试日志。

脚本不持久化任何请求或响应数据。GitHub Actions 不上传包含网络内容的 Artifact。

## 测试设计

测试全部离线运行，通过伪造 HTTP Session 或响应对象覆盖：

- 必需环境变量齐全时构造原始请求，且请求体不发生编码变化。
- 每个必需环境变量缺失时快速失败，错误只包含变量名。
- 未配置 Cookie 时不发送 Cookie 请求头；配置后原样发送。
- 2xx 且存在非空 `Result` 时返回成功。
- 非 2xx、网络异常、无效 JSON、非对象 JSON、缺失 `Result` 和空 `Result` 时返回失败。
- 日志不包含测试用 Token、AppIdentity、签名、Cookie、请求体或响应密文。
- 工作流只引用预期的 `EHI_*` Secrets，并可由 YAML 解析器读取。
- 现有 GLaDOS/Railgun 测试保持通过。

自动化测试不向真实一嗨接口发请求。真实凭据更新后的首次验证通过手动工作流执行，并在 App 中人工确认签到状态和积分变化。

## 文档与运维

README 增加独立的一嗨签到章节，说明：

- 如何从同一个 `SignIn` 请求获取所需字段。
- GitHub Secrets 名称和 Cookie 的可选规则。
- 响应加密导致的成功判定限制。
- 如何通过 App 人工完成首次验证。
- Token 失效或协议变化后需重新捕获整组请求，不能只替换其中一个字段。
- 静态重放属于已验证的临时兼容方案，不承诺长期有效。

## 验收标准

- 一嗨签到通过独立脚本和独立工作流运行，不改变现有 GLaDOS/Railgun 行为。
- 仓库和 Actions 日志中不出现真实认证数据、请求体或完整响应密文。
- 请求按捕获值原样重放，程序不尝试生成或修改签名相关字段。
- 服务端返回 2xx 和非空 `Result` 时工作流成功，否则明确失败。
- 文档不会把 HTTP 200 等同于可解密的业务成功，并要求首次配置后在 App 中人工核验。
- 离线测试覆盖配置、请求构造、错误处理、脱敏和工作流 Secret 引用。
