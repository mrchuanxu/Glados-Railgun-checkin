# GLaDOS 随机每日签到与周期兑换设计

## 背景

当前 GitHub Actions 每天在两个固定时刻运行，`checkin.py` 每次运行都会调用兑换接口。虽然配置中定义了兑换积分门槛，但现有代码没有在兑换前使用查询到的积分进行判断，也没有跨工作流保存兑换周期。

本次修改的目标是：每天在北京时间固定窗口内随机执行一次签到；按每个账号与域名分别累计有效签到日；达到配置周期后，根据实时积分兑换当前可负担的最高档位；兑换未成功时每 5 个自然日重试，成功后重新计时。

## 范围

本设计包含：

- GitHub Actions 的随机时间门控和每天防重复机制。
- 签到、积分查询、周期判断与自动兑换流程。
- 跨工作流运行的状态持久化。
- 新的兑换周期配置及 README 文档更新。
- 不访问真实服务的自动化测试。

本设计不包含：

- 新增其他通知渠道。
- 修改 GLaDOS API 协议。
- 为状态数据引入外部数据库或第三方服务。
- 与本次行为无关的代码重构。

## 已确认的行为

### 每日随机签到

- 定时工作流在北京时间 `12:00–18:00` 之间每 15 分钟触发一次。
- 每个北京时间自然日生成一个唯一的伪随机目标时间，候选时间为 `12:00` 至 `17:45` 的 15 分钟时间点。
- 目标时间之前的定时触发直接结束。目标时间到达后的首次可用触发执行签到。
- 当天已有一次真实执行后，后续定时触发直接结束。
- 工作流设置并发锁，同一仓库的两个签到任务不得并行执行。
- GitHub 调度可能延迟；实际开始时间可略晚于目标时间，但不会主动在窗口外选择目标时间。
- 手动触发立即执行，但仍遵守北京时间当天最多一次。手动执行后，当天定时触发不再签到。
- 门控跳过不会安装业务依赖、调用 GLaDOS API 或发送 PushDeer 通知。

### 有效签到日

- 每个“Cookie 标识 + 域名”是一个独立任务，分别保存计数和兑换状态。
- Cookie 标识由 Cookie 内容的不可逆哈希生成，状态文件不得包含 Cookie 明文。
- 签到接口返回成功或重复签到时，该任务当天计为一个有效签到日。
- 签到失败时不增加有效签到日。
- 同一任务在同一北京时间自然日最多增加一次计数。
- 首次部署或没有可恢复状态时，首次成功或重复签到记为第 1 天。

### 兑换周期

- 新环境变量为 `GLADOS_EXCHANGE_INTERVAL_DAYS`。
- 允许值为 `20`、`30`、`50`，默认值为 `30`。
- 配置缺失时使用默认值；配置无效时输出警告并使用默认值。
- 原有 `GLADOS_EXCHANGE_PLAN` 不再使用，并从工作流和 README 中移除。
- 当有效签到日达到配置周期时，任务进入到期状态，并在当天尝试兑换。
- 到期后计数保持在周期值，不再继续增加，直到兑换成功。

### 按积分选择兑换档位

签到后通过当前域名的 `/api/user/points` 查询实时积分。积分字段以字符串返回，程序使用十进制定点数解析，避免浮点边界误差。

程序始终选择当前积分可负担的最高档位：

| 积分范围 | 操作 |
| --- | --- |
| `points >= 500` | 兑换 `plan500` |
| `200 <= points < 500` | 兑换 `plan200` |
| `100 <= points < 200` | 兑换 `plan100` |
| `points < 100` | 不兑换 |

档位门槛来自已确认的接口响应：`plan100` 为 100 积分、`plan200` 为 200 积分、`plan500` 为 500 积分。接口动态返回的 `plans` 可用于日志或校验，但本次实现只支持以上三个已知档位；未知档位不得被自动调用。

### 到期重试与重置

- 到期当天若积分不足 100、积分查询失败或兑换失败，保持到期状态。
- 下一次兑换尝试日期设为北京时间的 5 个自然日后。
- 等待期间仍每日签到，但不重复尝试兑换，也不继续增加到期计数。
- 到达重试日期后的每日真实执行会再次查询积分并选择最高可兑换档位。
- 再次失败时，将下一次尝试日期继续顺延 5 个自然日。
- 只有兑换接口明确返回成功时，才将有效签到日清零、清除到期和重试状态，并记录成功日期。
- 兑换成功后的下一个有效签到日从第 1 天重新累计。

## 组件设计

### 工作流调度与门控

工作流负责：

1. 按 15 分钟粒度触发。
2. 恢复最新状态 Cache。
3. 根据北京时间日期计算当日目标时间。
4. 检查当日完成标记并决定跳过或继续。
5. 仅在继续执行时安装依赖并运行签到程序。
6. 无论业务步骤是否完全成功，都尝试保存已原子写入的状态。

伪随机目标时间必须由稳定输入派生，使同一天的所有触发得到相同结果。稳定输入至少包含仓库标识和北京时间日期。它不用于安全决策，只用于让每日执行时间发生变化。

### 状态存储

状态以带版本号的 JSON 文件保存，并通过 GitHub Actions Cache 跨运行恢复。Cache 使用每次保存唯一的键，并通过固定前缀恢复最近状态，避免覆盖不可变 Cache。

状态至少包含：

- 状态格式版本。
- 最近一次完整执行的北京时间日期。
- 每个任务的不可逆标识与域名。
- 每个任务最近一次尝试签到的日期。
- 有效签到日计数。
- 是否处于兑换到期状态。
- 下一次允许兑换的日期。
- 最近一次兑换成功日期。

业务程序在每个任务完成后采用临时文件替换方式原子保存状态。若程序中途退出，后续触发可跳过当天已经尝试过的任务，并继续尚未尝试的任务。当所有当前配置的任务当天均已尝试后，才写入当天完整执行标记。

Cookie 更新会产生新的不可逆标识，并作为首次出现的任务重新计时。这是避免保存敏感 Cookie 或引入外部账号映射的明确取舍。

### 签到与兑换协调

每个任务按以下顺序运行：

1. 检查最近尝试日期；今天已经尝试则跳过该任务。
2. 查询剩余天数并签到。
3. 查询最新积分，供结果展示以及可能的兑换使用。
4. 根据签到结果更新有效签到日。
5. 若刚到期或已到重试日期，根据积分选择兑换档位。
6. 调用兑换接口并根据明确的成功响应重置或安排下次重试。
7. 保存任务状态并继续下一个任务。

单个任务失败不得中断其他 Cookie 或域名。汇总通知应区分签到结果、当前计数、是否到期、兑换结果和下一次重试日期。

## 错误处理

- Cookie 缺失：保持现有的明确错误并停止业务执行。
- 周期配置无效：记录警告并使用 30 天。
- 积分无法解析：视为积分查询失败，不尝试兑换，若已到期则安排 5 天后重试。
- 状态 Cache 缺失：记录提示并以空状态首次启动。
- 状态 JSON 损坏或版本不支持：记录显著警告，保留损坏文件供日志定位，并以空状态继续；不得在不确定状态下立即兑换。
- Cache 保存失败：工作流失败或给出显著警告，以便用户发现状态未持久化。GLaDOS 的重复签到响应仍可防止重复增加有效签到日。
- API 或网络错误：记录到对应任务结果，不影响其余任务。
- 兑换响应不明确：一律按失败处理，不清零计数。

GitHub Actions Cache 不是永久数据库。如果 Cache 因平台策略丢失，系统会安全地重新计时，最坏结果是推迟兑换，而不是在未知周期下过早兑换。

## 测试设计

测试使用 Python 标准库 `unittest` 和模拟响应，不调用真实 GLaDOS 服务。覆盖：

- 周期配置 20、30、50、默认值和无效值。
- 北京时间日期边界、随机目标候选范围、目标前后门控和当天防重复。
- 成功、重复和失败签到的计数差异以及同日幂等。
- 第 20、30、50 个有效签到日进入到期状态。
- `99.99`、`100`、`199.99`、`200`、`499.99`、`500` 等积分边界。
- 积分不足、查询失败和兑换失败后的 5 个自然日重试。
- 成功兑换后的计数与重试状态清理。
- 多 Cookie 和多域名状态隔离。
- 中途失败后跳过已尝试任务并恢复未尝试任务。
- 空状态、损坏状态、版本不支持和 Cookie 明文不落盘。
- API 请求使用所选计划，未知计划不被调用。

工作流还需进行 YAML 语法检查，并验证门控跳过时不会安装依赖或调用签到脚本。

## 验收标准

- 每个北京时间自然日最多进行一次真实的批量签到执行。
- 定时执行的目标时间每天变化，且目标位于 12:00–17:45 的 15 分钟候选点。
- 每个 Cookie 与域名独立累计有效签到日。
- 仅在到期或 5 天重试日调用兑换接口。
- 兑换档位严格按实时积分选择最高可负担的已知计划。
- 兑换成功后清零；积分不足或失败时保持到期状态并顺延 5 个自然日。
- 状态文件不含 Cookie 明文，并能通过 Cache 跨工作流恢复。
- 自动化测试覆盖主要边界和失败路径，README 与实际配置一致。
