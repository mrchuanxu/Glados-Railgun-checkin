# 直接 Cron 每日门控设计

## 背景

现有工作流在北京时间 12:00–18:00 之间频繁触发，并额外计算一个每日随机目标时间。只有达到目标时间后的 cron 才能签到。GitHub Actions 的定时任务可能延迟或被丢弃，因此可能没有任何一次 cron 恰好在随机目标时间之后可靠到达。

本次变更取消随机目标时间，只保留“当天是否已经完成”的轻量门控。当天第一条实际到达的 cron 立即执行，之后的 cron 全部跳过。

## 调度行为

- 保留北京时间 `12:00–17:45` 每 15 分钟触发一次的 cron。
- 保留北京时间 `18:00` 的兜底 cron。
- 不再生成或比较每日随机目标时间。
- 每次触发恢复状态后检查 `last_complete_date`。
- `last_complete_date` 不是当天时立即放行。
- `last_complete_date` 已是当天时直接结束。
- 实际签到时间是当天 12:00–18:00 期间第一条成功创建并运行的 cron，而不是预先计算的随机时间。
- 如果部分 cron 被 GitHub 延迟或丢弃，后续 cron 仍可补偿执行。

## 防重复行为

- 工作流级门控在安装依赖和调用 API 前拦截当天后续运行。
- `checkin.py` 继续按“Cookie 标识 + 域名”检查 `last_attempt_date`，作为任务中断后恢复时的第二层保护。
- 所有当前任务完成一次尝试后，程序写入当天的 `last_complete_date`。
- `workflow_dispatch` 手动触发同样遵守当天最多一次；当天已完成时不强制重复签到。
- 门控跳过时不安装依赖、不调用 GLaDOS API、不发送 PushDeer 通知，也不保存新的 Cache。

## 组件变化

### `schedule_gate.py`

- 删除随机时间常量、哈希选点和 `daily_target`。
- 门控结果不再包含 `target_time`。
- 决策只依赖北京时间日期和 `last_complete_date`。
- 未完成时返回允许执行；已完成时返回跳过。
- 保留北京时间转换和 GitHub 输出写入。

### GitHub Actions 工作流

- cron 表达式保持不变。
- Cache 恢复、并发锁和条件执行保持不变。
- 门控步骤继续调用 `schedule_gate.py`，但日志只报告北京时间日期和是否已完成。

### README

- 删除“每天选择随机时间”的说明。
- 明确说明每天在 12:00–18:00 期间由第一条实际到达的 cron 执行签到。
- 说明后续 cron 通过当天完成状态跳过。

## 错误处理

- Cache 缺失或状态损坏时按当天尚未完成处理，允许执行；业务状态继续按现有安全策略重新计时。
- 如果业务程序在写入完整完成标记前失败，后续 cron 可以再次启动。
- 已成功保存的单任务 `last_attempt_date` 会让恢复运行跳过该任务，继续未完成任务。
- 如果业务程序完成但 Cache 保存失败，后续 cron 可能再次启动；逐任务 `last_attempt_date` 只能在状态成功恢复时提供保护。这是使用 Actions Cache 的既有限制。

## 测试

- 未设置 `last_complete_date` 时，定时触发立即放行。
- `last_complete_date` 是昨天时立即放行。
- `last_complete_date` 是今天时跳过。
- 手动触发在今天未完成时放行，已完成时跳过。
- 北京时间日期边界仍正确。
- GitHub 输出包含 `should_run` 和 `beijing_date`，不再包含 `target_time`。
- 删除随机目标稳定性、候选范围和目标前后判断测试。
- 现有签到计数、兑换周期和 5 天重试测试继续通过。

## 验收标准

- 代码中不存在每日随机目标时间计算。
- 当天第一条实际到达的 cron 可立即开始签到。
- 当天完成后，后续 cron 不安装依赖且不调用业务脚本。
- 每个北京时间自然日最多完整执行一次批量签到。
- cron 频率、兑换周期、积分档位和 5 天重试行为不变。
- README 与实际调度行为一致，所有自动化测试通过。
