# GitHub Actions 延迟容忍调度设计

## 背景

仓库当前使用 GitHub Actions `schedule`，计划在北京时间 12:00–16:00 每 15 分钟触发。实际运行记录显示，GitHub 会延迟或丢弃部分定时事件：正常日期的首条事件通常延迟到 12:28–12:39，严重时事件会在凌晨或次日才投递。

本次设计以“尽量每天成功签到”为首要目标。任务即使在预期窗口外到达，也允许作为北京时间当天的首次执行进行补签。

## 调度策略

将主要 cron 从整点及标准 15 分钟边界错开 7 分钟：

```yaml
- cron: '7,22,37,52 4-7 * * *'
- cron: '0 8 * * *'
```

对应北京时间：

- `12:07、12:22、12:37、12:52`，以相同节奏持续到 `15:52`。
- `16:00` 保留为最后一轮。

错峰用于降低 GitHub 整点高负载对调度的影响，不构成准点执行保证。GitHub 延迟投递后，工作流不因实际时间超出 12:07–16:00 而拒绝执行。

## 延迟补签与防重复

- `schedule_gate.py` 继续使用 Runner 实际启动时的北京时间日期。
- 若 `last_complete_date` 不是当天，立即放行业务步骤。
- 若 `last_complete_date` 已是当天，跳过依赖安装、签到、通知和 Cache 保存。
- 严重延迟的前一日事件在次日凌晨到达时，可以成为次日的首次签到。
- 批量任务完成后写入当天的 `last_complete_date`。
- 每个 Cookie 与域名的 `last_attempt_date` 继续作为中断恢复时的第二层防重复。
- `workflow_dispatch` 与定时事件使用相同门控，不强制重复签到。

此策略选择每日成功率而非固定执行时刻。不能保证某个自然日一定由原计划属于该日的 cron 事件执行，只保证实际到达后按当天状态处理。

## 可观测性

工作流增加不含敏感信息的诊断输出，至少包含：

- `github.event_name`。
- 对定时事件输出 `github.event.schedule`，手动事件明确标记为手动触发。
- Runner 实际启动时的 UTC 时间和北京时间。
- Actions Cache 恢复步骤的 `cache-matched-key`；没有匹配时显示“未恢复状态 Cache”。
- 门控计算的北京时间日期、`should_run` 和原因。

诊断日志不得输出 Cookie、PushDeer 密钥、Secret 值或完整状态文件。

## 运行历史保留

删除 `Mattraks/delete-workflow-runs` 步骤，避免成功运行被自动删除。GitHub 平台自身的保留策略继续适用。

保留 `liskin/gh-workflow-keepalive`，因为它与本次延迟诊断和运行历史删除无直接冲突。

## Cache 与失败行为

- 状态 Cache 成功恢复时，后续延迟事件能识别当天已完成并跳过。
- Cache 缺失、过期或保存失败时，工作流可能再次调用签到接口。
- GLaDOS 返回“重复签到”时，现有业务逻辑将其视为当天有效签到，不会造成同一状态文件内的重复计数。
- Cache 丢失会让兑换周期安全地重新计时，这是现有持久化方案的已知限制。
- 诊断日志应让 Cache 未命中和门控放行原因清晰可见。

## 测试设计

- 工作流只包含 `7,22,37,52 4-7 * * *` 和 `0 8 * * *` 两条 cron。
- 枚举北京时间触发点，确认从 12:07 开始、主要间隔为 15 分钟，并以 16:00 结束。
- 门控在凌晨或其他窗口外时间、当天未完成时仍放行。
- 当天已完成时，无论实际时间为何均跳过。
- 工作流包含事件类型、cron、UTC、北京时间和 Cache 匹配键诊断。
- 诊断步骤不引用 `secrets` 上下文，也不读取 Cookie 环境变量。
- 工作流不再引用 `Mattraks/delete-workflow-runs`。
- 现有签到、兑换周期、重试和状态隔离测试继续通过。
- GitHub Actions YAML 可解析。

## 验收标准

- cron 避开主要的整点和标准 15 分钟边界，同时保留 16:00 最后一轮。
- 实际到达时间超出窗口不会单独导致任务跳过。
- 每个北京时间自然日完成后，后续可恢复状态的运行均跳过业务步骤。
- Actions 页面保留成功和跳过运行，能够审计延迟情况。
- 日志足以区分事件计划、实际启动时间、Cache 恢复和门控结果，且不泄露 Secret。
- README、规格、工作流和测试保持一致。
